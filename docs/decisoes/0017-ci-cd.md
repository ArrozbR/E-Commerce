# 0017. CI com merge bloqueado e CD com aprovação manual e SSH restrito

- **Status:** Aceito
- **Data:** 2026-09-29
- **Relacionado:** `docs/DEFINICOES.md` D28, D29, §10.2–§10.3

## Contexto

Sem CI, testar depende de lembrar de rodar os testes. O autor preferiu deploy contínuo, que tem dois riscos: uma credencial de acesso ao servidor guardada no GitHub, e o checklist ponta a ponta nunca ser executado.

## Decisão

**CI (GitHub Actions, gratuito para repositório público).** O merge na `main` é bloqueado se falhar: build (avisos como erro), testes unitários, testes de integração, gitleaks, `dotnet format --verify-no-changes`. Trabalho via **PRs**, com **proteção de branch sem bypass, inclusive para administradores**.

**CD:**
1. Imagem **ARM64** publicada no GitHub Container Registry, com tag = hash do commit.
2. **Environment `production` com aprovação obrigatória do autor.** É o momento de executar o checklist ponta a ponta. A chave SSH fica guardada só no Environment.
3. SSH com um usuário **`deploy`** restrito por **comando forçado** no `authorized_keys` (`command="/opt/keycapstore/deploy.sh",no-pty,no-port-forwarding,no-agent-forwarding`). Esse usuário **não** está no grupo `docker`, e só pode executar o script via `sudo`.
4. `deploy.sh` valida a tag, faz o deploy **pelo digest** da imagem, aplica as migrations como **passo explícito** e reinicia a aplicação.
5. Endurecimento do workflow: `permissions` mínimas, actions fixadas por **hash de commit**, nada de `pull_request_target`, `known_hosts` fixado, **2FA** na conta do GitHub.

Voltar para uma versão anterior = disparar o deploy com a tag anterior.

## Alternativas consideradas

- **Só testes unitários no CI:** deixaria de fora a camada que protege contra concorrência e idempotência.
- **Ponta a ponta no CI:** exigiria chaves da Stripe no GitHub, dependeria de rede e seria instável.
- **Push direto na `main`:** a proteção de branch perderia o sentido.
- **Deploy manual (build na VM):** a imagem em produção não seria a mesma que o CI testou.
- **CD em que o servidor puxa a imagem:** considerado. O autor preferiu o CD completo, com as proteções acima.
- **Migrations na inicialização da aplicação:** risco de ciclo de reinicializações com o banco pela metade, e de corrida entre instâncias.

## Consequências

- **Positivas:** a imagem testada é exatamente a que roda; uma chave vazada só consegue executar o deploy; o autor mantém o controle de cada release.
- **Negativas:** configuração inicial trabalhosa (é o grosso do M0). Se passar do timebox, o plano B é um deploy manual simples no M0, com o endurecimento movido para o M6.
- **Pendente (Q4):** confirmar a disponibilidade dos runners ARM do GitHub para repositórios públicos.
- **Como saber se deu errado:** merges passando com o CI vermelho; deploys sem aprovação.
